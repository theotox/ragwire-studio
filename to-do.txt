## STEP 2: INFRASTRUCTURE & DOCKER COMPOSE

## STEP 3: `llama.cpp` ENDPOINTS, CONCURRENCY PROTECTION & RUNTIME SETTINGS

Store all model configurations in SQLite (seeded from `.env` on first startup) so **Admins** can update them live via the UI without restarting containers:

1. **Chat & Vision LLM (`http://100.69.140.69:8080/v1`, model `chat`):**

   - Qwen3.8-next with multimodal vision (`--mmproj`), `--parallel 2`, and `--reasoning-format deepseek`.

   - **Concurrency Protection (`MAX_CONCURRENT_VLM_CALLS=1`):** Because the remote `llama-server` runs with `--parallel 2` (two unified KV slots), guard background Vision photo-ingestion calls with an `asyncio.Semaphore(MAX_CONCURRENT_VLM_CALLS)` (default `1`). This guarantees bulk photo uploads queue cleanly and never starve interactive user chat requests of the second KV slot.

   - Stream responses via OpenAI-compatible SSE (`stream=True`).

   - Parse DeepSeek reasoning tags (`<think>...</think>` and/or SSE `reasoning_content` deltas) separately from the main answer so the UI renders them in a collapsible **"Thinking Process"** accordion.

2. **Embedding Model (`http://100.90.101.96:8082/v1`, model `bge-m3`):**

   - `bge-m3` (`--embedding --pooling mean --ctx-size 8192`). Configure Qdrant collection with Cosine distance and auto-detected embedding dimension (1024 for `bge-m3`).

3. **Reranker Model (`http://100.90.101.96:8083/v1/rerank`, model `reranker`):**

   - `qwen3-reranker-8b` (`--reranking --ctx-size 2048`).

   - **CRITICAL:** Keep RAGWire chunks around **512 tokens** with **64-token overlap** so `query + chunk` pairs never exceed the reranker's `2048`-token context limit.

   - Support Cohere/Jina-compatible `/v1/rerank` (with automatic fallback to `/rerank` if 404).

4. **Admin Model Settings UI:**

   - Editable fields for Chat URL/Model/API Key, Embedding URL/Model/API Key, Reranker URL/Model/API Key, `retrieval_top_k` (default `20`), `rerank_top_n` (default `5`), `rerank_score_threshold`, and `max_concurrent_vlm_calls` (default `1`), plus a **"Test All Connections"** button checking Chat, Embeddings, Reranker, and Qdrant health.

## STEP 4: USERS, RBAC & AUTHENTICATED FILE ACCESS

Implement JWT authentication (`POST /api/auth/login`, `GET /api/auth/me`, `POST /api/auth/change-password`) with 3 roles:

1. **`normal_user`**:

   - Create/manage/delete **only their own** Projects and chat histories.

   - Upload/delete/retry files in their own Project's dedicated library.

   - Attach/detach shared Knowledge Libraries to their own Projects.

2. **`library_operator`** (Knowledge Library Operator):

   - Everything a `normal_user` can do (and like Normal Users, sees **only their own** Projects and chat histories).

   - Create shared Knowledge Libraries, upload/delete/retry documents inside shared Knowledge Libraries, and delete shared Knowledge Libraries **ONLY when `usage_count == 0`** (enforce strictly on backend with HTTP `409 Conflict` and disabled button + tooltip on frontend).

3. **`admin`**:

   - Everything `library_operator` and `normal_user` can do.

   - Create/delete users and assign/update roles (`normal_user`, `library_operator`, `admin`). Prevent deleting the last remaining Admin.

   - View **ALL users' Projects** (and their chat histories) via an **"All Projects (Admin View)"** toggle, and delete **any** Project.

   - Edit global LLM / Embedding / Reranker settings.

4. **Authenticated File & Photo Delivery (`GET /api/files/{document_id}/content`):**

   - Never serve `/data/uploads` publicly without authorization. Serve original files and source photo thumbnails/lightboxes through `GET /api/files/{document_id}/content` validating either the `Authorization: Bearer <jwt>` header or a short-lived signed file token query parameter (`?token=...`) so standard `<img>` tags render cleanly while verifying the user has access to the document's library (shared library -> any authenticated user; project-dedicated library -> project owner or `admin`).



Seed `INITIAL_ADMIN_EMAIL` (`admin@rag.local`) and `INITIAL_ADMIN_PASSWORD` (`admin`) automatically on first startup.

## STEP 5: KNOWLEDGE LIBRARIES & PROJECTS ARCHITECTURE

Use a single unified Qdrant collection with payload filtering (`library_id`):

1. **Shared Knowledge Libraries (`is_project_dedicated = False`):**

   - Created by `library_operator` or `admin`.

   - Fields: `id`, `name`, `auto_summary` (concise 1–2 sentence auto-generated description), `created_by`, `usage_count` (count of Projects currently attaching this library), `created_at`, `updated_at`.

   - **Automatic Concise Summary Generation:** Whenever documents finish indexing in (or are deleted from) a shared Knowledge Library, asynchronously call the configured Chat LLM (`:8080/v1`) with representative chunks from the library to generate/update a **super concise summary (20–35 words)** describing the library's contents so Normal Users can pick the right libraries for their Projects.

   - Visible to all authenticated users in the Project library selector.

2. **Projects:**

   - Fields: `id`, `name`, `description`, `owner_id`, `dedicated_library_id`, `created_at`.

   - Creating a Project automatically creates one dedicated internal Knowledge Library (`is_project_dedicated = True`) bound 1-to-1 to that Project for project-specific uploads.

   - Attaching a shared Knowledge Library increments its `usage_count`; detaching decrements its `usage_count`.

   - **Clean Cascade Project Deletion (Zero Rubbish Left Behind):** Deleting a Project must atomically:

     1. Delete all Qdrant vectors matching `dedicated_library_id`.

     2. Delete the directory `/data/uploads/<dedicated_library_id>/` from disk.

     3. Decrement `usage_count` for every shared Knowledge Library attached to that Project.

     4. Delete all chat sessions, chat messages, document records, and the `dedicated_library_id` row from SQLite.

## STEP 6: MULTIMODAL INGESTION, DEDUPLICATION, RETRY & ASYNC WORKER

Support uploading: **PDF (`.pdf`), Word (`.docx`), Excel/Spreadsheets (`.xlsx`, `.xls`, `.csv`), Text/Markdown (`.txt`, `.md`), and Photos (`.jpg`, `.jpeg`, `.png`, `.webp`)**.

1. **SHA-256 Duplicate File Detection:**

   - Compute each uploaded file's `sha256` hash on arrival and store `file_hash` on the `Document` record.

   - If an identical file hash already exists in the **same** library (with status `indexed`, `processing`, or `queued`), skip duplicate re-ingestion and return a clear notification (`"Duplicate file skipped: already exists in this library as <filename>"`) so users don't accidentally pollute Qdrant with duplicate chunks.

2. **Async Background Worker & Failed-Job Retry:**

   - Upload endpoint saves unique files to `/data/uploads/<library_id>/`, inserts `Document` records with `status = "queued"`, and dispatches an async background worker task immediately.

   - Track states: `queued` -> `processing` (with step label like `"Waiting for VLM slot..."`, `"Vision analysis..."`, `"Chunking & embedding..."`, `"Updating library summary..."`) -> `indexed` or `failed` (`error_message`).

   - Implement `POST /api/documents/{document_id}/retry` (and a **"Retry"** action button in the UI on any `failed` document) that clears any partial Qdrant vectors for `document_id`, resets status to `queued`, and re-runs ingestion without requiring the user to re-upload the file.

   - Show live ingestion progress badges and polling/SSE updates in both the **Project Sources Drawer** and the **Knowledge Libraries Manager**.

3. **Multimodal Photo Pipeline:**

   - For `.jpg`, `.jpeg`, `.png`, `.webp` files: acquire the `MAX_CONCURRENT_VLM_CALLS` semaphore, base64-encode the image, and send it to the Vision-enabled Chat LLM (`:8080/v1`, model `chat`) to extract a rich, factual visual & OCR description. Embed that description with `bge-m3` and store `is_image=True`, `document_id`, and `image_url="/api/files/<document_id>/content"` in Qdrant payload metadata.

## STEP 9: MANAGEMENT SCRIPTS & VERSION-STAMPED INSTALLER BUILDER

1. **Management Scripts (`scripts/` and symlinked/copied to root):**

   - `start.sh`: Starts the stack via `docker compose up -d` and waits for healthchecks.

   - `stop.sh`: Gracefully stops containers via `docker compose down`.

   - `status.sh`: Displays current `VERSION`, container states (`docker compose ps`), disk usage of volumes, and backend `/api/health` + `/api/version` status.

   - `logs.sh`: Tails logs (`docker compose logs -f --tail=100`).

   - `backup.sh`: Creates a timestamped backup archive of SQLite DB, `.env`, and uploads.

2. **Installer Builder (`build-installer.sh`):**

   - Create `build-installer.sh` that reads `VERSION` from the root `VERSION` file and packages the entire application (source code, `docker-compose.yml`, Dockerfiles, `scripts/`, `.env.example`, and an embedded `install.sh` entrypoint) into a self-extracting, version-marked installer file:

     `dist/ragwire-studio-installer-v${VERSION}.sh`

   - When `ragwire-studio-installer-v${VERSION}.sh` is executed on a fresh target Linux VM:

     1. Verifies `docker` and `docker compose` (v2) are installed (exiting with clear instructions if missing).

     2. Prompts for or accepts `--install-dir` (default `/opt/ragwire-studio`) and `--port` (default `3000`).

     3. Extracts all application files, preserves any existing `.env` on upgrades (or generates a fresh `.env` with a new random `JWT_SECRET_KEY` on fresh install), writes `VERSION`, makes all `.sh` scripts executable, builds the Docker images (`docker compose build`), and runs `./start.sh`.
